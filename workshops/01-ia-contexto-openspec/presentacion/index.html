Bloque 1 · Claude Code¿Qué es?

Un chat responde. Un agente, además, hace cosas.

Claude Code es un agente: una IA que, además de contestar, puede trabajar sobre tu proyecto.

  • Lee los archivos de la carpeta que abres.
  • Escribe y edita código y documentos.
  • Ejecuta comandos en la terminal: Git, Docker, instalar dependencias…
  • Comprueba lo que ha hecho y corrige si algo falla.
Chat normal

"¿Cómo creo una tabla en una base de datos?"

Te da una explicación. Lo aplicas tú.

Claude Code

"Añade una tabla de notas a la base de datos."

Mira tu proyecto, escribe el cambio, lo ejecuta y te enseña qué ha tocado.

Insistir en que tú sigues decidiendo: el agente propone y ejecuta, pero lo que entra en el proyecto lo revisas tú.

El modelo (en la nube)

La "inteligencia" está en los servidores de Anthropic. Ahí se envía lo que escribes y lo que Claude lee de tus archivos.

Por eso: nada de contraseñas ni datos de clientes en los archivos del proyecto. Van en .env, que no se sube.

En el taller usamos Accept edits: los cambios se aplican y se revisan en la vista de diferencias (+12 −1 sobre el chat). La carpeta que se abre es la raíz del repositorio.
Bloque 1 · Claude CodeContexto fijo

AGENTS.md: lo que siempre debe saber

Las reglas del proyecto se escriben una vez, en AGENTS.md. Es un nombre estándar que entienden varias herramientas de IA.

  • Claude Code no busca AGENTS.md: lee CLAUDE.md. Por eso cada CLAUDE.md solo contiene @AGENTS.md, que le dice "carga ese archivo".
  • En cascada: el de la raíz se carga al abrir. El del taller, en cuanto Claude trabaja con archivos de esa carpeta. Si chocan, manda el del taller.
  • Abre siempre la raíz del repositorio. Si abres la carpeta del taller, se pierden las reglas generales.
AGENTS.md ← reglas de todo el repo CLAUDE.md ← solo: @AGENTS.md .claude/skills/ ← skills (siguiente bloque) workshops/ └── 01-ia-contexto-openspec/ ├── AGENTS.md ← reglas del ejercicio ├── CLAUDE.md ← solo: @AGENTS.md ├── brief/ ← qué construir └── proyecto/ ← tu código
Qué va en un AGENTS.md

Convenciones, restricciones, dónde está cada cosa, qué no hacer. No va: documentación larga que solo hace falta a veces, ni secretos.

Comprobado con Claude Code 2.1: abriendo la raíz carga los dos AGENTS.md; abriendo la carpeta del taller solo carga el del taller. Las restricciones del ejercicio son contexto activo: si una propuesta se las salta, Claude lo dice.
Bloque 2 · Skills y OpenSpec.claude/skills/<nombre>/SKILL.md

Una skill es un manual que se carga solo cuando hace falta

Cada skill empieza con una descripción de cuándo usarla. Claude lee esas descripciones y decide cuál aplica según lo que le pidas.

¿Por qué no meterlo todo en AGENTS.md?

Porque el contexto es limitado. AGENTS.md es lo que siempre aplica; una skill, lo que aplica en una situación concreta. Así la IA no carga instrucciones que no necesita.

Las de este repositorio

git-basico

Ramas, commits, deshacer, conflictos, Pull Request. Prueba: "me he liado con git, ayúdame".

entorno-local

Docker, puertos ocupados, base de datos, el archivo .env.

revision-de-entrega

Comprueba tu proyecto contra las restricciones. Prueba: "revisa mi entrega".

Hoy solo se usan; escribir skills es otro taller. Pedir que prueben "me he liado con git, ayúdame" para ver una skill en acción.
Bloque 2 · Skills y OpenSpecopenspec init · OpenSpec 1.12

OpenSpec instala seis comandos, cada uno con su skill

Se escriben en el chat de Claude Code empezando por /. openspec init se lanza una vez, en la raíz del repositorio.

/opsx:exploreopenspec-explore

Pensar en voz alta: opciones, preguntas, pros y contras. No escribe nada.

/opsx:proposeopenspec-propose

Escribe el plan: propuesta, especificación, diseño y lista de tareas. No toca código.

/opsx:applyopenspec-apply-change

Implementa las tareas del plan, una a una. Aquí se escribe el código.

/opsx:archiveopenspec-archive-change

Cierra el cambio y actualiza las especificaciones para que describan cómo es el sistema hoy.

/opsx:updateopenspec-update-change

Corrige un plan ya escrito y mantiene coherentes sus documentos. No toca código.

/opsx:syncopenspec-sync-specs

Pasa la especificación del cambio a las especificaciones principales sin archivar todavía.

Borde oscuro: el ciclo principal · borde claro: de apoyo, cuando hacen falta.

Si los comandos no aparecen: openspec init se lanzó en otra carpeta, o hay que abrir una sesión nueva para que se recarguen.

Bloque 3 · Describir bienAntes de /opsx:propose

La propuesta es tan buena como la descripción que le das

Poco útil

"Hazme una app de notas."

La IA tiene que inventarse el resto: qué campos, qué pasa si falla algo, qué queda fuera. Lo que se invente, lo vas a tener que corregir.

Útil

"Una app web para que una sola persona cree, vea, edite y borre notas. Cada nota tiene título obligatorio de máximo 120 caracteres y contenido opcional. Si el título está vacío, no se guarda y se explica por qué. Antes de borrar, pide confirmación. Fuera de alcance: login, etiquetas y búsqueda. Está terminada cuando las notas siguen ahí después de apagar y encender."

  • Para quién y para quéQuién la usa y qué problema le resuelve.
  • Qué entra y qué noUna lista de lo que queda fuera evita que crezca sola.
  • Cuándo está terminadaPruebas concretas que puedas hacer tú en el navegador.
El ejemplo "útil" sale del enunciado del taller (brief/app-de-notas.md). Para pasárselo entero a Claude: escribir @ y empezar a teclear app-de-notas.
Bloque 3 · Describir bienRevisar la propuesta

Buenas prácticas para escribir y revisar el plan

  • Describe comportamiento, no tecnología. "Las notas sobreviven a un reinicio", no "usa PostgreSQL". La tecnología se decide en explore y va en design.md.
  • Cuenta los casos difíciles. Título vacío, lista vacía, una nota que ya no existe. Son los que separan algo terminado de algo a medias.
  • Usa ejemplos concretos con valores reales: "121 caracteres", no "un título largo".
  • Un cambio cada vez. Si te sale una lista enorme, pártela en varios cambios.
  • Si no lo sabrías explicar, pregunta. "¿Qué es esto y por qué lo has elegido?"
  • Corrige el plan, no el código. Si cambias de idea, /opsx:update antes de seguir implementando.
Así queda un caso en spec.md
### Requirement: Título obligatorio El sistema SHALL impedir guardar una nota sin título o con un título de solo espacios. #### Scenario: Título vacío - WHEN la persona guarda una nota con el título " " - THEN la nota no se guarda - AND se muestra "El título es obligatorio"

Cada caso CUANDO → ENTONCES es algo que puedes comprobar tú en el navegador. Si no se puede comprobar, está mal escrito.

Preguntas de revisión: ¿cubre todos los casos del enunciado? ¿cumple las cinco restricciones del AGENTS.md del taller? ¿hay algo que no sabría explicar? ¿sobra algo?

Bloque 4 · El ciclo completoProbar en local

"Que arranque" no es "que funcione"

En local significa en tu portátil: la app y su base de datos corren en contenedores de Docker.

$ docker compose up # levantar app y base de datos $ docker compose down # apagar los contenedores $ docker compose up # ¿siguen tus notas?
http://localhost:<puerto>

El puerto es el número de puerta por el que se entra a la aplicación. Se configura en tu .env.

Recorre la lista del enunciado
  • Se levanta con un solo comando en una máquina limpia.
  • Sin notas, la pantalla dice que no hay ninguna todavía.
  • Creas, abres y editas una nota, y se ve bien.
  • Una nota sin título no se guarda y te explica por qué.
  • Apagas y enciendes: las notas siguen ahí.
  • Al borrar, pide confirmación.

¿Algo no arranca? Copia el error tal cual y pregunta por qué pasaba, no solo cómo arreglarlo. Ahí entra la skill entorno-local.

Las dos pruebas que más fallan: el título vacío y la persistencia tras docker compose down. Cuando todo pase, "revisa mi entrega" dispara la skill revision-de-entrega.
Para llevarteFin de la presentación

Tres ideas que quedan cuando se apaga el portátil

  1. El contexto manda

    El resultado de una IA depende sobre todo de la información que le das. AGENTS.md y las skills son esa información, escrita en archivos.

  2. Acuerda antes de programar

    Una propuesta revisada es más barata que código corregido. Lee el plan entero antes de /opsx:apply.

  3. Probado, no solo hecho

    Algo está terminado cuando has recorrido la lista en el navegador y los datos sobreviven a un reinicio.
